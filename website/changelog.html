[Fork 0.5.2-zd3.1] - 2026-11-16

First ZDownloader3 fork build. Imports upstream Mister Download Manager and re-identifies it natively Linux-first with a JDownloader2 look.

Added

  • JDownloader2 look: two-tab main window (Downloads / Linkgrabber), flat JD2-style theme (View → Theme → JDownloader2, default on Linux), toolbar with JD2-tinted icons (green Start/Resume, red Stop), dock panels on both tabs (Download Overview, File Properties / Linkgrabber Overview, Package Properties) with View-menu toggles
  • Linkgrabber grouping: packages form from the folder links share (across hosts, with a file-class constraint), or from archive volume names (host ignored), as JD2 packs
  • Packagizer (Downloads → Packagize&r): the rule chain (URL/name regexes, extensions, size bounds, stop-after-rule) to move/rename/redirect links, with variables <filename>, <name>, <ext>, <packagename>, <index>, <simpledate:…> and capture groups $1…${name}
  • Rename in-tree identity to ZDownloader3; Adwaita theme default replaced by JDownloader2 on Linux; settings migration adopts pre-fork data folders
  • Fork documents: NOTICE.md (provenance), docs/jd2-internals.md (decompiled JD2 analysis), docs/mdm-borrow.md (borrowing ledger, GPL boundaries), docs/gap-plan.md, docs/packagizer.md

Notes

  • Upstream features kept: engine with IDM-beating speed, torrents, Click'n'Load, extraction (zip/7z/rar), debrid services, browser extension + remote control + automation API + MCP, 86 languages, Linux .deb/.rpm/AppImage packaging
  • JD2 assets are never copied; analysis informed layout/behavior only

Changed

  • Videos are looked up about a second sooner on Windows (#1053): MDM installs yt-dlp's folder build there, which starts in half a second, instead of the single program, which unpacks itself at every start and took 1.3 s. Every look-up gains it: the qualities in the menu over a video, the Download video window, a video's download. Measured here from the look-up's start to its qualities: a YouTube video in about 3.7 s instead of 5.4 s, a TED talk in about 1.9 s instead of 3.8 s. A copy an earlier version installed is replaced in the background the first time MDM looks a video up, even for the same version of yt-dlp; a yt-dlp you chose yourself in Helpers stays as it is. The video button also starts its look-up a fifth of a second after the pointer rests on it, rather than only once it has shown over the video for 0.6 s, so a click made straight away finds it under way; and a click on a video whose early look-up MDM was too busy for (other videos' still running) asks again rather than opening the Download video window.
  • Bangla, reviewed by a native speaker for the main window, the download list, the progress window, the dialogs, the tray and the language picker: one word for each thing (Stop, Close and Turn off no longer share a word; nor do Remove and Move), Status and Invalid in the words Bangladesh uses, its spelling as written there, and the menus' keyboard letters on English letters in brackets, as in Hindi and Japanese: the Bangla letters they were on can't be pressed as shortcuts (#927; thanks to @geniusmonir).
  • Videos come down through MDM's own downloader: yt-dlp now finds a video and its sound, and MDM downloads them the way it downloads any file: over as many connections as Options → Connection gives (8 by default; the progress window's connections table and segment map show them), under the speed limits (a change applies at once), paused and resumed like a file, also after quitting MDM, and with a fresh address asked of yt-dlp when one expires. yt-dlp then joins them and adds the subtitles as before. YouTube's qualities, its sound, most sites' MP4s and streams in pieces (HLS, DASH) come this way, and so do an image gallery's pictures, which gallery-dl lists (gallery-dl 1.32 and later; it then fetches only what MDM couldn't have); live streams and RTMP, RTSP, MMS or FTP streams are still yt-dlp's to download, and the progress window says so (#769).
  • Building from source needs Rust 1.98 or later, CMake and libclang (and NASM on Windows): the browser-like connection is built on BoringSSL (#668).
  • Debrid accounts: signing in by code opens the page only when it is the service's own site, over https.
  • An idle MDM no longer redraws its window twice a second to watch the clipboard for copied links (Options → General → Offer to download links copied to the clipboard, on by default): the clipboard is looked at from a thread of its own, on Windows only when it changed, and the window is woken only when a new text was copied. A graphics card hardly noticed those frames, but Windows' software renderer (WARP, which draws where a card can't) spent most of a processor core on them: idle, MDM drawing with WARP now uses about a sixth of what it did (#847).
  • Windows: on a graphics card without Direct3D 12 (Intel's HD Graphics 3000 to 5500, older AMD Radeon cards), MDM still draws with OpenGL, and once OpenGL fails there it draws with Direct3D 12 on Windows' own software renderer (WARP) from the next start. OpenGL fails when it can't start, is too old to draw MDM, its first window doesn't show within 10 seconds, or MDM freezes inside the graphics driver while OpenGL shows a frame, as the freeze reports from those cards showed: the crash report's window reads that from the freeze and remembers it. View → Draw with says what draws and why (Direct3D 12 (WARP): this graphics card has no Direct3D 12 driver, OpenGL froze inside the graphics driver here); choosing OpenGL there tries it again. WARP failing too goes back to OpenGL, and is remembered. WARP draws with the processor, so OpenGL comes first where it works (#847).

Fixed

  • A crawling connection at a download's end is replaced again when the disk was slow: a connection that crawls (a bad path, a few KB/s) is reconnected rather than left to hold a last piece too small to share, but after a download whose disk had set the pace, it could hold that piece for a minute or more. The share of the line each connection is measured against was then learned only from the download's end, where the crawling connections were all that was left, so they read as fast enough. The line is now never taken for less than one connection brought over it. Found by the end-to-end tests on busy test machines, which failed now and then; under load, 13 runs in 90 failed before, none after.
  • The command line's video-get downloads videos it refused: with no quality given it asked for the best single file with both picture and sound, which a site such as Bilibili doesn't have (its pictures and sounds come apart), and failed with *Requested format is not available*. It now takes the quality the Download video window starts on, the best picture with the best sound joined to it (with ffmpeg), as the window does. The new -q/--quality takes a height (-q 1080, 720p): the best of that height, or the nearest below it the page offers, and says which it took (a quality event with --json). What the download's log says comes too (a quality the servers don't give, taken at the nearest below), and when no format matches, the error lists those the page offers, as video-info does (with --json, as choices and yt-dlp's own formats) (#1240).
  • Create new queue opens its name box in front: Create new queue in the Categories tree's right-click menu, or in a download's Add to queue / Move to queue, opened the Scheduler with Enter queue name behind it, where it couldn't be seen; the Scheduler waited for that box, so none of its buttons did anything and no queue could be created. The box now stays in front of the Scheduler and takes the keys, as the question before deleting a queue does, also when the Scheduler is clicked while it is open. And the name it proposes is one no queue has: with Queue # 3 deleted and Queue # 4 kept, it proposed Queue # 4 again, which OK refused until the name was changed (#1237).
  • macOS: dialogs (Download File Info, Add URL, Download video, Add torrent, confirmation prompts, and others) and download progress windows activate MDM and open in front of browsers and other applications (including when opened or raised from the menu bar icon while MDM is behind another app or hidden there), while keeping minimized or tray-hidden windows untouched and Download complete notices non-activating.
  • A menu's underlined letter no longer types into the box under it: with a text box's right-click menu open (Undo, Cut, Copy, Paste, Delete, Select all), pressing P pasted *and* typed a "p" into the box; the arrow keys that moved in the menu moved the box's caret too. While a menu is open (a right-click menu, the menu bar's), every key is now the menu's, as in Windows. The underlined letters of languages written in another script (Arabic, Russian...) now choose their item too, from a keyboard in that language. And in a dialog, Alt with a button's underlined letter no longer types that letter into the box that has the focus (not on macOS, where Option types letters).
  • Screen readers in the main window (NVDA, Narrator): the download list, the Categories tree and the toolbar can now be reached and used. Tab goes round the toolbar, the Categories tree and the download list (Shift+Tab the other way), and in each the screen reader says what the keys are on and follows them as they move: the download (its name, status and size, "2 of 40"), the category (with its count, open or shut) or the toolbar button. Until now none of them could take a screen reader's focus, so it never went into the list or the tree, and the toolbar's buttons weren't there for it at all. The toolbar is now a toolbar of named buttons (a greyed one is said to be unavailable): Left / Right, Home and End move along it, Enter or Space presses a button, Down or Alt+Down opens Add Torrent's or a queue button's menu. A screen reader can also move its focus to a download, a category or a button itself (it is chosen, and that part takes the keys), and the strip under the list reads as a status bar. The lists in MDM's windows (Options' browsers, a torrent's files, the Link grabber, the language picker...) now say their selected row as the arrows move it too, instead of only "list" (#1190).
  • The Add Mister Download Manager to your browser window and Options → General → Test browser integration no longer freeze MDM's window while a browser's folder is slow to answer. Both read whether the browsers can reach MDM from the browsers' own folders, the first one every second while it is open, and on the window's thread: on a Mac, one read waited 8 seconds and the window was reported as stopped responding (a sleeping disk, a home folder on the network, or macOS asking whether MDM may access another app's data do the same). They now read it beside the window, one read at a time, and show what they read last meanwhile (Checking... before the first answer). macOS: when macOS keeps MDM out of a browser's folder (*Operation not permitted*), both now say so, naming the browser and the folder, with what to do: allow it when macOS asks whether MDM may access data from other apps, or turn MDM on in System Settings → Privacy & Security → Full Disk Access, then Set it up (#1218; the Chrome folder refused in #1173's log).
  • A way of drawing that failed once is tried again: when Direct3D 12 (Vulkan, Metal) or OpenGL failed to show MDM's window, MDM remembered it and drew another way from then on, until you chose it again in View → Draw with. One slow start was enough: a laptop whose Direct3D 12 took 11 seconds to show its first window just after Windows started drew with OpenGL ever after, which its graphics driver handled worse. MDM now remembers when it happened, why, and on which graphics card and driver, and tries that way again after a graphics driver update (or another card), or once a while has passed: a week for a window that didn't show in time or a start that ended before it, a month for a way that couldn't start or froze inside the driver, and only after a driver update for an OpenGL too old to draw MDM. A try again that fails is remembered again and waits twice as long (up to three or six months), so a card whose driver fails every time doesn't cost a bad start every week. A first window late in the first minutes after you sign in, when the computer is busiest, is tried again at the next start. View → Draw with says since when MDM passes it over and when it tries it again, and so do crash reports (#1205).
  • macOS: no more The window stopped responding report while a file dialog is open. macOS runs its Open and Save dialogs (and the folder ones) on the thread that draws MDM's windows, which waits there until you answer: 9 seconds spent choosing a file were taken for a frozen window. The time a system dialog is open is no longer counted, and the log says when one opens and closes; a window still stuck once the dialog is closed is reported as before. Windows and Linux show their dialogs beside the window, which goes on drawing, so nothing changes there (#1192).
  • MDM's window opens at once when an unfinished download's file is on a network share that doesn't answer, or on a drive that is asleep. Before its first frame MDM read every unfinished download's progress from beside its file, and waited for each folder to answer: with one on a share that was off, the window took 21 seconds to appear (Windows gives up on such a share after about 21 seconds). The list now shows each download as it was last saved, and its progress as on the disk comes a moment later, read beside the window, a share that doesn't answer holding up only its own downloads. A download started or resumed meanwhile, by you or by a queue that starts with MDM, looks for its progress itself, beside the window too: the window no longer stopped responding for 21 seconds at each try of a download whose folder is gone, and the download fails on its own, its data kept, as before. Download video no longer reads the video's folder before the window can go on either: the new download shows its name at once and is numbered on, as before, when the folder has answered, and a video started before then waits for it (found with #1170).
  • macOS: MDM no longer closes when OpenGL can't make a texture (a picture it draws with: an icon, a page of letters), as it did when the displays changed while it drew with OpenGL (a dock with a monitor plugged in and the lid closed, with a second MDM window open). The system could leave MDM's thread without its OpenGL context, and MDM, which checked only that the context was still on its window, went on drawing without one: OpenGL refused the next new texture and MDM stopped. MDM now also checks that the context is its thread's own and takes it back when it isn't, and a texture OpenGL still refuses is kept and made on a later frame, with a line in the log, instead of closing MDM. View → Draw with → Metal was not affected (#1173).
  • Offer to download links copied to the clipboard no longer offers the same link again by itself: a moment when another program had the clipboard open was taken for an empty clipboard, so the link still on it came back as newly copied the next time the clipboard changed (Windows' clipboard history, a clipboard manager, Remote Desktop), and Download File Info opened for it over and over. A clipboard MDM can't read now is read again a second later, and only a link copied since is offered (#1157; thanks to @ADNM0 for finding it in the code).
  • No freeze when downloads are deleted with their files (Delete with Also delete the file from disk, Shift+Delete, Delete All Completed): the rows leave the list at once and their files are deleted beside the window, one after the other, instead of by the window, which waited for the disk at each file (8 seconds in the report, for one file: a disk that is slow, busy or waking up, a network or USB drive, an antivirus checking the file). A finished file that can't be deleted (open in a player) is still said, in one message however many there are, and a download added meanwhile under the same name is given a numbered name, so it is never the one deleted. Files still being deleted as MDM exits get a few seconds to go (#1170).
